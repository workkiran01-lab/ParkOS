## Newly found defects and limits

- A locally simulated broad table grant let authenticated TRUNCATE empty every tenant's memberships. Existing and future application-table TRUNCATE privileges are now revoked from PUBLIC, anon, authenticated and service_role. This was a local reproduction of privilege drift, not an observation of a hosted project.
- A phone-only auth row with NULL email accepted another email's admin invitation because SQL NULL inequality did not enter the refusal branch. The forward function uses IS DISTINCT FROM. NULL/wrong email now refuses with no profile/membership/invite writes; matching email still succeeds.
- The organization bootstrap, customer bootstrap and invite acceptance definers bypassed deactivation checks in table RLS. Each now checks account deactivation explicitly; all three have active-account controls and removal-of-guard mutations.
- Receipt generation's service-role reservation/facility/space/zone reads and receipt-number sequence usage were missing from explicit migration grants. The local native service role failed the query before the fix. The new verifier executes the joined query and numbered insert, then proves cross-tenant receipt isolation. It verifies database dependencies, not live Storage/email delivery.
- Receipt delivery remains explicitly best-effort in the existing product: a PDF/upload failure after the receipt row is claimed has no durable retry queue, and email can be skipped. Payment processing is not rolled back by this auxiliary failure. This run does not claim end-to-end receipt delivery or add an outbox/retry product workflow.
- Partial permit refunds and invoices settled by multiple PaymentIntents remain outside the single-payment permit ledger's full-refund model. The existing code warns/returns its explicit partial-refund outcome; this run verifies that response rather than silently presenting it as a recorded reversal.
- No Stripe account was used. Signature generation and verification use the pinned Stripe SDK locally. Current API field shapes were checked against official Stripe references; no authenticated Stripe request or hosted Supabase connection occurred.

## Premises corrected

1. Basil removed the Invoice object's `paid` field, not the `invoice.paid` event. The event still exists. The old field reader could produce INVOICE_NOT_PAID and HTTP500/retries; it is not accurate to describe every version of that failure as HTTP200. The baseline already contained corrected payload readers, so Task1 closes their untested dispatch/handler gap. [Invoice field changes](https://docs.stripe.com/changelog/basil/2025-03-31/add-support-for-multiple-partial-payments-on-invoices); [event types](https://docs.stripe.com/api/events/types).
2. Subscription periods moved to subscription items; the handler reads `items.data[0].current_period_start/end`. The app creates a single-price subscription. [Stripe period change](https://docs.stripe.com/changelog/basil/2025-03-31/deprecate-subscription-current-period-start-and-end).
3. The original issuance/permit overlap verifier is sequential, not a real concurrency test; its issued permit is pending, not active. Browser-closure and Stripe-failure labels denote database state scenarios, not executed external failures. Separate real-session tests are identified in the evidence.
4. The checkout verifier's expected 1200c cap was not valid at every wall-clock hour. CI produced 1212c when a moving fixture crossed LA midnight. Pricing was correct; the fixture now uses fixed same-local-day timestamps.
5. Removing USAGE alone does not necessarily break sequence access: nextval also accepts UPDATE. CI exposed that alternative grant. The mutation now removes both capabilities.
